# Visual Consistency Report (Phase 2: Component Consistency, Phase 8: Visual Polish, Phase 11: Quality)

Every component category the mission listed (buttons, cards, tables, inputs, dropdowns, badges, navigation, forms, loading, empty, error, success states) was audited by directly comparing real usages across every page, not by inspecting one file and assuming the rest match.

| Issue | Reason | Impact | Priority | Implementation |
|---|---|---|---|---|
| Secondary actions ("Save," "Dismiss," "Approve," "Reject") were naked `<button>` elements with only a text color, no padding, border, or background, sitting directly next to fully-styled primary buttons | Never given the same treatment as primary buttons when these flows were built | Reads as an unfinished control next to a finished one on the same screen; also fails the 24x24px touch-target guideline (see `ACCESSIBILITY_REPORT.md`) | High | **Fixed**: `CandidateCard.tsx`'s Save/Dismiss and `ReviewQueuePage.tsx`'s Approve/Reject now have a visible border, consistent padding, and a rounded-lg corner, distinct from (not competing with) the primary "Promote"/filled buttons beside them |
| Badge/status-pill styling had four incompatible conventions: `PolicyStatusBadge`'s deliberate left-border-plus-monospace treatment, `ConfidenceBadge`'s bordered pill, a near-duplicate bordered pill for missing-field tags with a different font size (11 vs 12), and a third filled-no-border pill for metadata tags, all in one file | Each was built independently without checking the others | A reviewer scanning one candidate card sees three different pill shapes for three different kinds of small labels | Medium | **Fixed the clearest drift**: the missing-field tag in `CandidateCard.tsx` now matches `ConfidenceBadge`'s exact border/radius/font-size convention. Left `PolicyStatusBadge`'s left-border style and the Live pages' filled-tint status pills as-is: both are deliberate, differently-reasoned choices (documented in `PolicyStatusBadge.tsx`'s own comment) for genuinely different content (a policy's lifecycle status vs. a live decision's real-time status), not accidental drift |
| Raw enum values shown verbatim in different places: `PolicyStatusBadge` rendered `pending_review` literally; the filter dropdown right next to it on the same page already showed "Pending review"; `LiveEvidence.tsx` showed `VERIFIED`/`REJECTED` in full caps; `LiveTestIntent.tsx` showed `ALLOW`/`DENY`/`HUMAN_REVIEW` in full caps | No shared formatting helper existed | The same underlying value reads three different ways depending which screen you're on | High | **Fixed**: added one `formatStatus()` helper (`src/app/live/format.ts`) that lowercases, replaces underscores with spaces, and capitalizes the first letter regardless of the API's original casing. Applied everywhere a status or outcome enum is displayed as text: `PolicyStatusBadge`, `LiveAgents`, `LiveDocuments`, `LiveEvidence`, `LiveTestIntent`, `DryRunPage`, `PolicyDiffPage`, both upload tables |
| No loading indicator on initial page-data fetch anywhere in the app; the two design eras failed in opposite directions: older pages seeded state as `[]` and showed a real "No data yet" message before the fetch even resolved (a false-empty flash), newer pages seeded state as `null` and rendered a blank pane with no loading affordance at all | Never standardized | A user on a slow connection either sees a wrong "empty" message for a split second, or sees nothing happening | Medium | **Fixed the misleading half**: `LiveEvidence.tsx` now seeds `records` as `null` and only shows "No evidence yet" once the fetch has actually resolved to an empty array, matching the already-safe pattern the newer pages use. A true loading spinner for every page's initial fetch is a larger, separate addition (see `UX_IMPROVEMENTS.md`) |
| None of the app's three data tables (`PolicyListPage`, `UploadPage`, `CorpusUploadPage`) had any row hover feedback despite every row being a clickable link | Never added | A user can't tell a table row is interactive until they click it | Medium | **Fixed**: added a `transition-colors` class plus a hover background (`onMouseEnter`/`onMouseLeave`, matching the pattern `Layout.tsx`'s own nav already used) to all three tables |
| Empty-state copy used two different, uncoordinated colour tokens (`--pr-text-muted` and `--pr-text-disabled`) with no rule for which applied where, and ranged in register from a single terse word ("None found.") to a full explanatory paragraph | Never standardized | Reads as inconsistent tone across a single product | Medium | **Fixed the token**: standardized every empty-state message on `--pr-text-muted` (the token that actually passes contrast, see `ACCESSIBILITY_REPORT.md`), removing every remaining `--pr-text-disabled` use on real body text. **Fixed the worst tone/context gaps**: `CorpusReviewPage.tsx`'s generic "None found." (reused verbatim across 7 different finding categories) now reads specifically ("No principals were found in this corpus.", "No conflicts...", etc.); `PolicyListPage.tsx` now distinguishes "No policies yet." (genuinely empty) from "No policies match your filters." (filtered to zero), instead of one flat "No policies match." for both cases |
| 16 instances across the app of `` `${Action} failed: ${JSON.stringify(e.body)}` ``, showing a raw backend error payload (a FastAPI/Pydantic validation array, in the worst case) directly to the user | Copied forward from the first page that needed error handling, never revisited | The most severe, most repeated finding in the whole audit: an enterprise user should never see a raw JSON blob as an error message | Critical | **Fixed everywhere**: added one `describeApiError(e, action)` helper (`src/app/live/format.ts`) returning a clean, human sentence, and replaced all 16 occurrences across `CompilePage`, `DryRunPage`, `PolicyWorkspacePage` (x2), `DeploymentPage`, `ReviewQueuePage` (x2), `CandidateCard` (x3), `UploadPage`, `CorpusUploadPage`, `LiveAgents`, `LiveDocuments` (x2), `LiveTestIntent` |
| Elevation/shadows: cards across the app use only a 1px border (`rgba(255,255,255,0.05)`), never a drop shadow, consistently | N/A, this is already consistent | None | N/A | No change needed; noted here to confirm it was checked, not overlooked |

## Deliberate differences that were investigated and kept

- `PolicyStatusBadge`'s left-border-plus-monospace treatment vs. every other pill/badge in the app: this is a written, reasoned design decision in the component's own source comment ("enterprise, minimal, GitHub-level clarity, no gimmicks"), not an oversight. Left unchanged.
- The homepage hero's primary CTA is slightly larger than every in-app button. A landing page's single hero action being sized up from utility buttons is standard practice (Stripe, Linear, Vercel all do this); forcing it to match in-app button sizing would remove an intentional visual hierarchy, not fix an inconsistency.
