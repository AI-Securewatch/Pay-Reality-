# Part 20 — Architectural Assessment

**Supersedes/synthesizes:** nothing prior offers a single candid, cross-cutting critique — this part is new synthesis, not derived from an existing document. Judgments below are the author's own, formed from direct code reading across this entire specification, not a restatement of any file's self-description.

## 20.1 What's genuinely well-built

- **Fail-closed is enforced structurally, not by convention**, in the one place it matters most (`decision_engine.evaluate`, [12_DECISION_ENGINE.md](12_DECISION_ENGINE.md) §12.1) — there is exactly one code path to `ALLOW`, and every exception type and every ambiguous OPA result explicitly resolves to `HUMAN_REVIEW`. This is the single most important correctness property in the entire platform, and it is verifiably true by reading ~80 lines, not by trusting a design document's claim about it.
- **The domain/service/router layering has no cycles and is consistently applied** ([18_DEPENDENCY_GRAPH.md](18_DEPENDENCY_GRAPH.md) §18.3). This is what makes the Decision Engine, Compiler V2, and Evidence signing independently unit-testable with zero database dependency, and it is what let three genuinely large subsystems (Compiler V2, Agent Lifecycle, RBAC) get built alongside an existing, live system without ever needing to modify `decision_engine.py` itself.
- **Migrations are held to a real, enforced discipline** — every autogenerated migration this session required manual correction (missing `CheckConstraint`s, `None` constraint names), and every one was verified via `alembic check` plus a full `upgrade → downgrade → upgrade` round-trip against the real production database before being trusted. This is a level of rigor many teams only adopt after being burned by its absence once.
- **Compatibility bridges are deliberate, not accidental** — the `policies` table being kept alive as the Decision Engine's active-bundle pointer ([17_LEGACY_COMPONENTS.md](17_LEGACY_COMPONENTS.md) §17.4), the operator key remaining a permanent bypass alongside RBAC ([14_SECURITY_MODEL.md](14_SECURITY_MODEL.md) §14.1), the AI Policy Builder's promotion path reusing `create_policy` unmodified ([10_AI_POLICY_BUILDER.md](10_AI_POLICY_BUILDER.md) §10.4) — each is a considered choice to avoid touching working code, documented as such in the code itself, not an accident of incremental development.
- **The evidentiary chain of custody is real, not decorative.** Canonical serialization, published keys, a rotation registry that preserves historical verifiability, and (Phase 5) chain-linking that catches deletion, not just tampering — this is a coherent, load-bearing security property across four separate subsystems (signing, rotation, chaining, audit events reusing the same primitives), not four independent features that happen to sit near each other.

## 20.2 What's fragile or worth revisiting

- **The `policies` table's dual role is the single sharpest edge in the whole codebase.** It is correct, well-reasoned, and guarded (`UnexpectedActiveWriterError`) — but it is also exactly the kind of implicit cross-subsystem coupling that a future engineer, reading `db/models.py` cold, will misdiagnose as dead legacy cruft (this specification's own drafting process did so, initially, before direct production verification corrected it — see [17_LEGACY_COMPONENTS.md](17_LEGACY_COMPONENTS.md) §17.4). A one-line comment on the `Policy` class itself, pointing at `deploy_policy`, would close this gap cheaply.
- **The Decision Engine's `PolicyStore` abstraction is now serving a purpose it wasn't designed for.** It was built to abstract "how do we find the active policy" for testability; it now also carries the entire compatibility bridge between two authoring generations. That's a reasonable emergent use of an existing seam, but it means the abstraction's name ("PolicyStore") no longer fully describes what it does.
- **Field-vocabulary validation is a real, silent gap** ([07_RUNTIME_POLICY_ENGINE.md](07_RUNTIME_POLICY_ENGINE.md) §7.4, [16_CURRENT_LIMITATIONS.md](16_CURRENT_LIMITATIONS.md)) — a condition authored against a nonexistent field compiles cleanly and never matches, with no signal anywhere that anything is wrong. Given how much of this platform's value proposition rests on "the policy does what its author intended," this is the limitation most worth closing next, ahead of most feature work.
- **The AI Authority Builder's discovery-to-enforcement gap is a genuine product question, not just a technical one** ([09_AI_AUTHORITY_BUILDER.md](09_AI_AUTHORITY_BUILDER.md) §9.5): today, six of the eight discovered categories are purely informational, connected to the real Authority Model only by a human reader's judgment. Whether to build automatic (or semi-automatic, confidence-gated) promotion is a real design decision with real risk on both sides — automating it wrong would put unverified graph edges into an enforcement-adjacent structure; leaving it manual bounds how much of the Authority Builder's own value actually reaches enforcement.
- **The SDK's operator-key dependency for principal creation** ([11_AGENT_ARCHITECTURE.md](11_AGENT_ARCHITECTURE.md) §11.8) is a real gap between the RBAC model's own stated design goal (scoped, least-privilege credentials) and what the SDK actually needs out of the box. This is a small, well-scoped fix (a `PRINCIPAL_MANAGE`-scoped API key path already exists in the permission model — the SDK's default flow simply doesn't use it yet).
- **Single-instance assumptions are pervasive and currently invisible.** Rate limiting (in-process memory), OPA (embedded, loopback), and the general absence of any horizontal-scaling story mean this platform's current architecture is implicitly "one backend process" — true today, and fine today, but worth naming explicitly before it's tested by actual load rather than discovered under it.

## 20.3 Is the current abstraction level right?

Yes, largely — with one caveat. The lack of a DI framework, a repository pattern over SQLAlchemy, a task queue, or a cache layer is *correct* for this platform's actual current scale and request pattern (single backend process, request-scoped, synchronous, no background job to speak of). Introducing any of those now would be exactly the kind of premature complexity this platform's own conventions (see `domain/rbac/permissions.py`'s explicit reasoning: "a new permission is a real security decision... not a config toggle") consistently avoid elsewhere. The one place the abstraction is arguably *under*-built relative to what's already been asked of it is the `Vocabulary` seam in Compiler V2 ([07_RUNTIME_POLICY_ENGINE.md](07_RUNTIME_POLICY_ENGINE.md) §7.4) — it exists and is used correctly, but has never been exercised with a second real vocabulary, so its actual sufficiency for a genuine second domain is unverified, not just unbuilt.

## 20.4 What would most improve confidence in this system, ranked

1. **Field-vocabulary validation in Compiler V2** — closes a silent-failure class that directly undermines the "policy does what it says" guarantee this platform's whole pitch depends on.
2. **A one-sentence code comment on `Policy`/`policies`** pointing future readers at `deploy_policy` — the cheapest possible fix to the single most likely point of future confusion in this codebase.
3. **A real, live, external round-trip test of the SDK against the hosted production API** — not this session's own direct API calls, but an actual `pip install`, `Agent()`, `register()`, `authorize()` sequence run against the real hosted URL, to close the "unverified live SDK path" gap named in [16_CURRENT_LIMITATIONS.md](16_CURRENT_LIMITATIONS.md).
4. **A deliberate decision, one way or the other, on Authority Builder discovery → enforcement promotion** — not building it is a legitimate choice, but it should be a stated one, not simply the current absence of a feature.

## 20.5 Overall verdict

This is a codebase that has been repeatedly, genuinely stress-tested against its own claims rather than left to accumulate untested design documents — the `rego_generator.py` field-routing bug ([16_CURRENT_LIMITATIONS.md](16_CURRENT_LIMITATIONS.md) §16.3) and this specification's own correction about the `policies` table ([17_LEGACY_COMPONENTS.md](17_LEGACY_COMPONENTS.md) §17.4) are both examples of exactly this pattern: a plausible-sounding claim, caught wrong by direct verification, fixed, and re-verified. That habit — verify against the real system rather than trust the last thing that was written down — is the platform's actual strongest asset, more so than any single subsystem's design. The gaps in §20.2 are real, but every one of them is the ordinary residue of a system built by verification rather than a symptom of one built by assumption.
