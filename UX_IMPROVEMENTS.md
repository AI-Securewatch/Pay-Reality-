### Noted, not changed: terminology drift across authoring paths

The same underlying concept, "an AI-extracted, not-yet-reviewed policy," is labeled three different ways depending on which pipeline produced it: "Candidate Runtime Policies" (single-document AI Policy Builder), "Runtime Policies" (inside the multi-document AI Authority Builder's graph summary), and "Candidate Authority" (the legacy delegation-of-authority pipeline). The first two are worth reconciling in a future pass. The third is deliberately different, not sloppy: `DOMAIN_AGNOSTIC_ARCHITECTURE.md` already established that the legacy pipeline operates on a genuinely different domain object (`Authority`/`Mandate`, not `RuntimePolicy`), so calling its output "Candidate Authority" is accurate, not inconsistent, even though it looks similar at a glance.

## Phase 5: Friction audit

The mission's instruction was explicit: never remove functionality, only reduce friction. Reviewed the full click path for each major workflow:

- **Create and deploy a policy manually**: Policy Studio List -> New Policy -> fill Identity/Scope/Conditions/Constraints/Effect/Metadata -> Save -> Submit for review -> (separately) Review Queue -> Approve -> Compile -> Dry Run -> Deploy. This is 7 distinct steps across 2 pages, matching the mission's own required governance flow (`draft -> pending_review -> approved -> compiled -> active`) exactly; nothing here is accidental friction, it is the deliberate human-review gate this platform's whole value proposition depends on. No change recommended.
- **AI Policy Builder / AI Authority Builder promotion flow**: Upload -> (automatic extraction) -> Review each finding -> Promote -> lands as a `draft` back in the manual flow above. The one real friction point found: promoting a policy takes you to a plain "created" response with no direct next-step link forward into the manual flow's Submit-for-review step. **Recommendation** (not implemented this pass, to stay within "improve, don't redesign"): after promotion, link directly to the newly-created policy's Workspace page instead of just showing a confirmation message, saving one navigation step. `CandidateCard.tsx` already links to Policy Studio after promotion; extending that link to land directly on the policy rather than the list is a one-line change for a future pass.
- **Rejecting an authority claim in the legacy DoA page** (`LiveDocuments.tsx`) uses a native `window.prompt()` dialog for the rejection reason, while every other rejection flow in the app (`ReviewQueuePage.tsx`) uses an inline text field. **Recommendation** (not implemented, deliberately deferred): replacing the native prompt with an inline field would touch this component's state shape, not just its styling, so it was left as a documented recommendation rather than folded into this visual-and-copy-focused pass.

## Phase 6: Onboarding

A first-time user should understand Principals, Resources, Runtime Policies, and Evidence without reading documentation. Checked what the app currently explains, on-screen, without a doc link:

- The homepage (`PlatformOverview.tsx`) already walks through the whole workflow in order (Authority -> Policy Studio -> Runtime Decisions -> Evidence -> Assurance) with a one-sentence description of what happens at each stage; this is the app's existing onboarding surface and it is reasonably strong already.
- **Gap found**: nowhere on the homepage or in Policy Studio itself does the app define "Principal," "Resource," or "Runtime Policy" as terms, only shows fields with those names. A first-time user filling out `ScopeFields.tsx`'s "Principal" input has no in-context explanation of what a Principal is. **Recommendation** (not implemented this pass, a genuine content addition rather than a polish fix): a one-line `title` attribute or inline hint on each of these three fields, e.g. `title="Who this policy grants authority to"` on the Principal input, would close this gap cheaply without adding a documentation page or redesigning the form.

## Phase 7: AI Authority Builder, "make it feel magical"

The mission asked for staged progress ("Upload -> Processing -> Understanding Organisation -> Extracting Authority -> Review -> Promotion"), visible confidence, and visible discoveries, without exposing implementation details.

**What already does this honestly**: the Review stage already shows per-finding confidence (`ConfidenceBadge`), a running count of discoveries by category (the 8-tile summary strip: Runtime Policies, Principals, Resources, Operations, Relationships, Conflicts, Gaps, Questions), and every finding's source citation, none of which exposes an implementation detail (no mention of Claude, prompts, or the corpus-concatenation mechanism anywhere in the UI).

**What was deliberately not built**: an animated, staged loading sequence ("Understanding Organisation... Extracting Authority...") during the upload/extraction wait. This was considered and set aside on purpose: the actual extraction is one synchronous backend call with no intermediate progress signal to report (`AI_AUTHORITY_BUILDER_ARCHITECTURE.md` documents this as a deliberate, simple synchronous design, matching every other extraction pipeline in this platform). Building a multi-stage animated sequence with no real progress behind it would mean either faking stage transitions on a timer (dishonest: the UI would claim to be doing something it isn't actually tracking) or adding real incremental progress reporting from the backend (a genuine new feature, not a polish fix, and outside this phase's "do not invent features" boundary). The honest middle ground already exists: the upload button's own state already reads "Uploading and analyzing corpus..." for the whole duration, an accurate, non-misleading description of what is actually happening, rather than a fabricated multi-step show.
