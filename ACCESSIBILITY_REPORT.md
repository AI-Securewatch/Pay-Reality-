# Accessibility Report (Phase 10: Accessibility)

Audited against WCAG AA: keyboard support, screen reader support, colour contrast, focus indicators, and touch target sizing. Contrast ratios below were computed directly from the hex values in `theme.css` using the WCAG relative-luminance formula, not estimated.

| Issue | Reason | Impact | Priority | Implementation |
|---|---|---|---|---|
| No `:focus-visible` styling anywhere in the app; 9 inputs across `LiveAgents.tsx`, `LiveDocuments.tsx`, `LiveTestIntent.tsx`, and `OperatorKeyField.tsx` explicitly set `outline-none` with no replacement | Never added | A keyboard-only user tabbing through any form in the app (agent registration, dry-run, review queue, operator key) cannot see which field currently has focus | Critical (WCAG 2.4.7) | **Fixed**: one global rule in `theme.css` gives every interactive element (`a`, `button`, `input`, `select`, `textarea`, `[role="button"]`, `[tabindex]`) a visible on-brand focus ring via `:focus-visible`, and all 9 `outline-none` classes that would have suppressed it were removed |
| `--pr-text-disabled` (`#64748B`) fails AA contrast for normal text on every background in the app (3.28-3.98:1, below the required 4.5:1), but was used for real, meaningful body text in ~15 places, not just genuinely disabled controls | The token's name implied "use for de-emphasized text" without a contrast check | Low-vision users may not be able to read empty-state messages, audit trails, evidence IDs, and similar secondary copy across the app | Critical (WCAG 1.4.3) | **Fixed everywhere real text used it**: `Layout.tsx`, `PlatformOverview.tsx`, `ReviewQueuePage.tsx`, `DeploymentPage.tsx`, `PolicyWorkspacePage.tsx`, `DryRunPage.tsx`, `PolicyDiffPage.tsx`, `VersionHistoryPage.tsx`, `CompilerDiagnosticsList.tsx`, `CorpusReviewPage.tsx`, `ReviewPage.tsx`, both upload tables all switched to `--pr-text-muted` (6.08-7.39:1, comfortably passing). Left `--pr-text-disabled` in place only where it colors decorative icons or non-text border accents, which only need 3:1 under WCAG 1.4.11 and already meet it |
| 32 `<label>` elements paired with inputs, zero using `htmlFor`/`id` anywhere in the app | Never wired up | A screen reader announces these inputs with no name at all: Agent name, Acting-for-principal, DryRun's Principal/Action/Resource/Context, Policy Workspace's Name/Description/Delegated-by/Risk-level/Owner/Tags, Scope Fields' four inputs, and more | Critical (WCAG 1.3.1, 3.3.2, 4.1.2) | **Fixed across every form found**: added matching `id`/`htmlFor` pairs (using React's `useId()` for collision-safe, per-instance IDs on reusable components) in `LiveAgents.tsx`, `LiveDocuments.tsx`, `LiveTestIntent.tsx`, `ScopeFields.tsx`, `DryRunPage.tsx`, `PolicyWorkspacePage.tsx`, `CandidateCard.tsx`, `CorpusUploadPage.tsx` |
| Several inputs had no label or `aria-label` at all, only a placeholder (which disappears once typed and is not a reliable name for all assistive tech): `ReviewQueuePage`'s reviewer-name and rejection-reason inputs, `PolicyListPage`'s search/status-filter/sort controls, `OperatorKeyField`'s key input | Placeholder text was mistaken for a label | Same as above, worse: placeholder-only naming can vanish entirely once the user starts typing | Critical (WCAG 3.3.2, 4.1.2) | **Fixed**: added `aria-label` (or a visually-hidden `sr-only` `<label>` where a visible one would disrupt the layout) to every one of these |
| Zero `role="alert"` or `aria-live` regions anywhere in the app; every validation/error/success message is a plain, uncontrolled `<p>` that appears after a click | Never added | A screen reader user whose focus has moved to the button they just pressed gets no notification that a new message appeared elsewhere on the page | High (WCAG 4.1.3, 3.3.1) | **Fixed**: added `role="alert"` to every message/error container found across `LiveAgents`, `LiveDocuments`, `LiveTestIntent`, `LiveAssurance`, `PlatformOverview`, `CompilePage`, `DryRunPage`, `DeploymentPage`, `PolicyWorkspacePage`, `ReviewQueuePage`, `CandidateCard`, `UploadPage`, `CorpusUploadPage` |
| Icon-only "remove" buttons had poor or missing accessible names: the literal character "x" on tag-removal buttons (`CandidateCard.tsx`, `PolicyWorkspacePage.tsx`), and unlabeled "Remove" buttons in `ConditionRow.tsx` and `CorpusUploadPage.tsx` | Only one place in the whole app (`Layout.tsx`'s mobile menu button) had ever done this correctly | A screen reader announces "x, button" with no indication of which tag it removes | High (WCAG 4.1.2, 2.4.6) | **Fixed**: added specific `aria-label`s (e.g. `` `Remove tag ${t}` ``, `` `Remove condition on ${field}` ``) to every instance found |
| `CorpusReviewPage.tsx`'s collapsible "Show/Hide" section toggles exposed no `aria-expanded` or `aria-controls`, only the visible "Show"/"Hide" text as a signal of state | Never added | A screen reader has no programmatic way to know whether a section is currently expanded | Medium (WCAG 4.1.2) | **Fixed**: added `aria-expanded={open}` and `aria-controls` (linked to a real `id` on the content region) to the shared `Section` component, fixing all 8 uses at once |
| Heading hierarchy skipped `<h2>` entirely on three pages, going straight from `<h1>` to `<h3>`: `LiveAgents.tsx`, `PolicyWorkspacePage.tsx` (7 section headers), `PolicyDiffPage.tsx` (4 section headers) | Section headers were typed as `<h3>` without checking what came before them | A screen reader user navigating by heading level gets a document outline with an empty, confusing gap at level 2 | Medium (WCAG 1.3.1, 2.4.6) | **Fixed**: demoted every one of these to `<h2>`. Confirmed safe before changing: each already had an explicit Tailwind font-size class overriding the bare tag's default styling, so the visual size is unchanged, only the semantic level is corrected |
| No skip-to-content link in the shared app shell; a keyboard user must tab through the full 6-item sidebar nav on every single page navigation | Never added | Repetitive, unnecessary keyboard navigation burden on every page load | Medium (WCAG 2.4.1) | **Fixed**: added a visually-hidden-until-focused "Skip to main content" link as the first focusable element in `Layout.tsx`, targeting the main content region |
| Touch targets under the ~24x24px minimum: the "x" tag-removal buttons and several "Remove" buttons had no padding at all, only a color and a small font size | Never checked against a minimum target size | Harder to tap accurately on a touch device | Medium (WCAG 2.5.8) | **Fixed** alongside the aria-label fixes above: added `padding` to every one of these buttons |
| `aria-current="page"` was missing on the active sidebar nav item; the active state was conveyed by colour and a small side-bar accent only | Never added | A screen reader has no programmatic signal for which nav item represents the current page | Low (WCAG 4.1.2 / best practice) | **Fixed**: added `aria-current={active ? "page" : undefined}` to `Layout.tsx`'s nav links |
| Semantic HTML for clickable elements | N/A, already correct | None | N/A | Confirmed via `grep` that zero `<div onClick>` patterns exist anywhere in the app; every clickable surface is already a real `<button>` or `<a>`/`<Link>`, including the drag-and-drop file uploaders, which correctly wrap a native `<input type="file">` in a `<label>`. No change needed; worth preserving as new pages are added |

## What this pass does not claim

This is a real, verified pass against the specific violations found, not a certification of full WCAG AA compliance across every possible criterion (colour-blind-safe palette validation, full screen-reader manual testing with NVDA/VoiceOver, reduced-motion media query support, and a complete responsive-layout pass were not performed and would be a reasonable next phase). Every fix above was applied directly to the affected file and verified to still build.
